# ihue Bid — project status

**Product**: a generic market-value discovery and offer collection platform (`bid.ihue.in`). A creator publishes a rich listing; participants anonymously say what they think it's worth; responses aggregate into a consensus price, a likely value band, and a confidence level. Full spec: `requirements/ihue-bid-project-requirements-and-solution.md`. Reuse assessment against the sibling project: `requirements/ihue-rating-reuse-assessment.md`.

**Stack**: Next.js 16 + React 19 + TypeScript + Tailwind 4, pnpm, Prisma 7. Auth (email OTP + Google OIDC), session cookies, SES email, Cloudinary media, and the app/server/lib layering were forked from the sibling project `/Users/prijith/proto/ihueRating` — same conventions, ihue-bid-specific domain.

**Credentials note**: `.env.local` intentionally reuses ihueRating's real AWS/SES, Cloudinary, **and Google OAuth** credentials (the user's explicit choice), same Cloudinary cloud with `CLOUDINARY_FOLDER_PREFIX=ihue-bid/development`, same Google OAuth client. `AUTH_SECRET` and `CRON_SECRET` were freshly generated for this app — never shared across apps.

**SES `FromAddress` is IAM-restricted, not just verification-restricted**: the shared IAM user (`atride-ses-sender`) has a policy allowing `ses:SendEmail` only when `ses:FromAddress` exactly matches one of `noreply@atride.in` / `ihue.india@gmail.com` / `noreply@ihue.in` (`StringEquals`, no subdomain/wildcard matching). `noreply@bid.ihue.in` was tried first in production and got a `403 not authorized` — not an SES-domain-verification failure, an IAM policy denial. `SES_FROM_EMAIL=noreply@ihue.in` (on the allowlist already) is used instead, both locally and in production, rather than editing the IAM policy. `SES_FROM_NAME` is `"iHue"` (matches ihueRating's, since the from-address is shared too). If a distinct `bid.ihue.in` from-address is ever wanted, that policy's `ses:FromAddress` list needs `noreply@bid.ihue.in` added first.
- **`EmailDeliveryError`'s real message used to be silently discarded**: `requestEmailOtp` (`src/server/auth/auth-service.ts`) catches SES failures and always re-throws a generic `AuthError("EMAIL_DELIVERY_UNAVAILABLE", ...)` for the client — correct (never leak provider errors to users) but the original error's message was thrown away entirely, not even logged, making production failures undiagnosable from Vercel's logs. Fixed with one `console.error` before the re-throw. If email delivery ever silently fails again, check Vercel's Logs panel for a request to `/api/auth/email/request`, expand its per-request log, and look for `Email delivery failed <reason>`.
- **A second, unrelated failure surfaced once `FromAddress` was fixed**: `403: The request signature we calculated does not match the signature you provided` — a SigV4 signature error, meaning AWS couldn't validate the credentials at all, not an authorization problem. Root cause was `AWS_SECRET_ACCESS_KEY` getting corrupted when manually retyped/pasted into Vercel's env var UI (it contains a `+` character, a common corruption point for copy-paste). Fixed by deleting and re-adding `AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`/`AWS_REGION` in Vercel from a clean source rather than editing in place. General lesson: a SigV4 "signature does not match" error means the credential value itself is wrong/corrupted, not a permissions or `FromAddress` issue — don't chase IAM policy theories for that specific error text.

**Google OAuth redirect URI is per-domain, not per-account**: reusing ihueRating's OAuth client works immediately for `localhost:3000` (both apps' local `APP_URL` matches an already-authorized redirect URI on that client) but needed `https://bid.ihue.in/api/auth/google/callback` added explicitly to that same client's authorized redirect URIs in Google Cloud Console before it worked on the deployed domain (done — confirmed live, no more `redirect_uri_mismatch`).

**Deployment**: live on Vercel at `bid.ihue.in` (custom domain attached, DNS via GoDaddy), confirmed working end-to-end including real SES email delivery and Google sign-in. Production env vars mirror `.env.local` with `EMAIL_PROVIDER=ses` (mock is hard-blocked in production by the code itself) and `APP_URL=https://bid.ihue.in`. Vercel env var changes require an explicit redeploy to take effect — they don't hot-reload into already-running serverless functions.

**Database**: provisioned — Neon project `ihue-bid` (ap-southeast-1), migrated and working. `DATABASE_URL`/`DIRECT_URL` are live in `.env.local`, and the same database is reused for production (no separate prod branch yet — a deliberate simplicity choice while there's no real traffic).

**Deliberate deviations from ihueRating's conventions** (documented so they don't look like drift):
- `Listing.publicId` is an app-generated, short, URL-safe id (`src/server/listings/public-id.ts`), not a DB-generated UUID like every other table's `id`. This is required by the product spec (§5): internal UUIDs must never appear in public listing URLs (`bid.ihue.in/{handle}/{publicId}`). `Listing.id` itself is still the normal UUID primary key.
- Category-specific listing fields live in a generic `ListingFieldValue` key/value table rather than dedicated columns, so a future category template doesn't require a schema migration. `src/server/listings/templates/used-vehicle.ts` is the first (only) template, and drives both the creator's structured-field form and the public listing display.

## Built so far (foundation slice)
- Auth: email OTP + Google OIDC, session cookies (`ihue_bid_session`), forked from ihueRating with product-name strings updated.
- Creator handle: `src/server/account/profile-service.ts` — lowercase-normalized, reserved-word-checked (`src/server/account/reserved-handles.ts`) against platform routes, with a real settings UI at `/account/settings` (ihueRating has the same underlying `UserProfile.handle` column but no UI to set it — this app builds that UI). Same settings page also edits the **display name** (`User.displayName`, seeded from the sign-in email at signup, previously uneditable): `setUserDisplayName()` in `profile-service.ts`, `POST /api/account/display-name`, `<DisplayNameForm>`.
- Public creator profile at `/{handle}` — avatar, bio, location, verification badge, list of live/closed listings.
- Listings: `Listing` + `ListingFieldValue` + `MediaAsset` (ordered gallery) + `ExternalEmbed` (YouTube) + `ReferenceLink`. Creator flow: `/dashboard/listings/new` (create draft) → `/dashboard/listings/[id]/edit` (photos, video, reference links, publish) → public page at `/{handle}/{listingId}`.
- Media: Cloudinary sign → upload → server-verify flow forked from ihueRating, generalized so `LISTING_IMAGE` uploads append to a gallery (`MediaAsset`, ordered) instead of overwriting a single column like `USER_AVATAR` still does.
- Used Vehicle template: `src/server/listings/templates/used-vehicle.ts` — the one concrete instance of the generic template framework §6.2 calls for. In the create form (`create-listing-form.tsx`), the vehicle-details section comes first, then "Listing basics" (title/description/location), then pricing. `suggestListingTitle()` / `suggestListingDescription()` (pure + unit-tested) build a title (`modelYear make model variant fuelType transmission`) and a prose description (registration year + km + owner count + service-history/accident/defect notes) from the details — offered as an **Apply** suggestion, shown only while that field is still empty so later detail edits never overwrite typed text.
- Anonymous valuation responses: `ParticipantIdentity` + `Response` models, a signed first-party cookie (`ihue_bid_participant`, `src/server/participant/`) independent of the authenticated session, one active `Response` per participant per listing (upsert-in-place on revision, `revisionCount` tracked — no separate audit-history table yet). Submission at `POST /api/listings/[id]/responses`, only accepted while `status === "LIVE"`; value is snapped to the listing's increment and clamped to its range server-side regardless of client input (`src/server/listings/response-value.ts`, pure + unit-tested). UI: `PriceSlider` (`src/components/price-slider.tsx`) is a circular drag/keyboard slider — same geometry engineering as ihueRating's `rating-slider.tsx` (`src/lib/price-slider-geometry.ts`, pure + unit-tested), generalized from a fixed 0–10 domain to an arbitrary `[min, max, step]` price range, styled in Bid's blue instead of Rating's OKLCH rainbow (that gradient is semantically tied to Rating's 0–10 score identity, not reused). `ValuationForm` wraps it with submit/revise state; the public listing page resolves any existing valuation server-side from the participant cookie to prefill the slider.
  - **Named estimates (added later):** a participant may optionally attach a name (`ValuationForm` name field + "Keep this estimate anonymous" checkbox). `Response.contributorName` is a per-response snapshot (non-null ⇔ "named"); `ParticipantIdentity.displayName` is the remembered name, written whenever a non-empty name is supplied **regardless of the anonymous checkbox** (so it prefills on the next listing) — the checkbox only controls attribution of *that* estimate. `normalizeContributorName()` (`response-value.ts`, pure + unit-tested) trims/collapses/caps at 80. `POST /api/listings/[id]/responses` takes `{ name, anonymous }`. Named estimates are shown **publicly and to the creator, with their values** — the form copy says so (deliberate disclosure, same "contact over ceremony" instinct).
- Aggregation & result display: `src/server/listings/aggregation.ts` — pure, unit-tested `computeAggregate()` — median consensus + 25th/75th-percentile band (resistant to outliers by construction, per §8.2), a sample-count-driven confidence tier (`< 5` LOW / `5–14` MEDIUM / `≥ 15` HIGH — a starting heuristic; §9.2's "poor diversity / suspicious pattern" downgrades aren't wired in since that needs the anti-abuse work below), fixed-width distribution bins, and the §8.3 green/yellow/red/purple expectation-vs-consensus wording (purple = wide dispersion, checked before the color comparison). `getListingAggregate()` in `response-service.ts` is the single source of truth for which rows count (filters `mode: ANONYMOUS_VALUATION`) — both the public page and the creator dashboard call it, so the filter can't drift between them the way it did in ihueRating's `attachRatingSummaries`. Presentational `<AggregateResult>` (`src/components/aggregate-result.tsx`) renders on the public listing page (only when `Listing.resultVisibility === "PUBLIC"`, a new creator-configurable field alongside `ownerPriceVisibility`, settable at creation only for now) and always on the creator's dashboard edit page regardless of that setting. `getListingAggregate()` now returns `{ all, named, counts, namedEstimates }` (named = aggregate recomputed over non-anonymous responses only; `partitionNamedValues()` in `aggregation.ts`, pure + unit-tested). The client `<AggregateResultPanel>` (`aggregate-result-panel.tsx`) wraps `<AggregateResult>` with a "Skip anonymous" checkbox (shown only when there are both named and anonymous responses) that toggles which dataset renders, plus a "Named estimates" list (name + value). Used on both the public page and the dashboard edit page.
- Closing flow: creator closes a `LIVE`/`PAUSED` listing with an outcome (`ClosureOutcome`: `SOLD`/`NOT_SOLD`/`REMOVED`, optional final price/note) and a `closureVisibility` (`SHOW_OUTCOME`/`CLOSED_ONLY`, mirrors `resultVisibility`) via `src/server/listings/closing-service.ts`. A minimal, real notification opt-in (`NotificationOptIn` model, email + OTP-style verification reusing `OtpChallenge`/`OtpPurpose.CONTACT_VERIFY` — new service functions in `src/server/participant/notification-service.ts`, deliberately *not* `auth-service.ts`'s `requestEmailOtp`/`verifyEmailOtp`, since a participant must never get a `User`+`Session` as a side effect) lets a participant who already submitted a valuation ask to be emailed when the listing closes. Closing sends each verified opt-in a real email (`src/server/email/closure-notification-template.ts`) with a per-recipient magic-link token generated fresh at send time (**not** at opt-in time — the token's raw value only ever needs to exist once, when building the email, so generating it early and only storing its hash would make it unrecoverable later; caught this before shipping it, see git history) pointing at `/{handle}/{listingId}/interested?token=...`. **Contact-sharing model (revised — earlier commits describe the old one):** the verified opt-in email is disclosed to *that listing's* creator at opt-in time — the `NotifyOptInForm` says so explicitly ("shared with the creator so they can follow up — no one else"). The creator sees the full list of verified opt-ins on their dashboard edit page (`getListingParticipantContacts`, any non-draft status), each `mailto:`-linked, so they can reach out while the listing is still live. `stillInterestedAt` is no longer a consent gate — clicking "I'm still interested" on the post-close magic link is now just a "yes, still want it" signal that badges that row in the creator's list. (History: this was once notify-only, with the email hidden until the participant clicked "still interested"; `NotificationOptIn.sharedContactWithCreator` was dropped even earlier as redundant with `stillInterestedAt`. The creator explicitly wanted to contact interested people directly, so the disclosure moved up-front instead.) One recipient's send failure is logged and skipped, never blocks the close itself or other recipients (no outbox/retry queue — not needed at expected per-listing volumes).

- Anti-abuse (baseline controls, §9.1): `RateLimitAttempt` (`src/server/security/rate-limit.ts`, `checkRateLimit()`) — same IP-hash-plus-counter-table pattern as ihueRating's `internal-testers` route, the only anti-abuse precedent in either codebase — applied to every public write endpoint (`responses`, `notify-opt-in/request`+`verify`, `interested`, `auth/email/request`+`verify`) with per-endpoint thresholds (5/15min for real-email-sending endpoints, matching ihueRating's own numbers; looser elsewhere). Same honeypot convention (hidden `company` field, silently reports success without persisting if filled) on the two public data-entry forms, `ValuationForm` and `NotifyOptInForm`. Also closes a real gap: `Response.revisionCount` was tracked but never enforced — `checkRevisionAllowed()` (`src/server/listings/response-value.ts`, pure + unit-tested) now caps revisions at 20 and requires a 30-second cooldown between them, exactly what §9.1 calls for and nothing was doing until now.
- Gemini-suggested price range, creator-only: `src/server/ai/gemini-client.ts` forks only `callGemini()` from ihueRating's version (structured-JSON-output mode; the image-gen/transcribe variants aren't needed here), reusing the same live `GEMINI_API_KEY`/`AI_ASSIST_ENABLED`. `src/server/ai/price-suggestion.ts` builds the prompt from *every* filled Used Vehicle fact (ownership count, service history, accident disclosure, accessories, modifications, known defects, both years, km, fuel, transmission, registration location) except `vin` — deliberately excluded, since it has zero bearing on price and requirements §6.2 treats it as sensitive/opt-in-to-publish — and validates/clamps the AI's response (swaps a reversed low/high, rejects non-positive or non-numeric values) before anything downstream sees it, same discipline as ihueRating's `normalizeAnalyzeOutput`. `POST /api/listings/suggest-price` is session-gated and rate-limited (10/15min — costs real Gemini usage per call). Surfaces only on `create-listing-form.tsx` as a "Suggest a range" button that fills `responseMin`/`responseMax` — never the public page, and never `ownerExpectedPrice` (that field is the seller's actual ask, a different concept than a market estimate). Verified live against the real Gemini API — the rationale it returned explicitly referenced the ownership count and service history fields, confirming they're actually reaching the model, and the VIN sent in the test never appeared in the response. `hasSufficientFactsForSuggestion()` (make/model/modelYear required) is enforced **server-side** in `price-suggestion-service.ts`, not just as the button's client-side disabled state — the structured-output mode can't refuse to answer, so a UI-bypassed empty request would otherwise get back a confident-looking but entirely ungrounded price range, indistinguishable from a real one. Same function is imported client-side too (`create-listing-form.tsx`), so the two checks can't drift.

- UI / design system (full makeover): semantic theme tokens in `src/app/globals.css` via Tailwind v4 `@theme inline` (`bg`, `surface`, `muted`, `border`, `fg`, `body`, `muted-fg`, `subtle-fg`, `accent`, `accent-soft` — light values in `:root`, dark in `.dark`), plus a **dark mode** (`@custom-variant dark`, class on `<html>`, flash-free inline script in `layout.tsx`, `ThemeToggle` in the header persisting to `localStorage["ihue-bid-theme"]`). Shared primitives in `src/components/ui/` (`Button`/`buttonClasses`, `Card`, `Field`+`inputClass`/`selectClass`/`textareaClass`, `StatusPill`/`Pill`, `EmptyState`+`icons`, `Stat`/`StatRow`) and a shared `<ListingCard>` used by the dashboard, public profile, and the landing feed. `layout.tsx` now wraps a flex column with a new `<SiteFooter />`. Every existing page and component was swept to the tokens (no behaviour change). Landing page (`src/app/page.tsx`) rebuilt into marketing sections — hero with a mock `<AggregateResult>` visual, "how it works", **live public-listings feed** (`listRecentPublicListings()` in `listing-service.ts` — cross-creator, `status: LIVE`, creator must have a handle), trust principles, closing CTA. Dashboard and public profile got stat strips + card grids + designed empty/onboarding states (`listListingsForCreatorWithStats` / `listPublicListingsForHandleWithStats` add a per-listing `responseCount` via one `response.groupBy`). Public listing page is now a two-column sticky-panel layout. No schema or API changes.
- Loading/click feedback: `loading.tsx` route skeletons for the four dynamic segments (`[handle]`, `[handle]/[listingId]`, `dashboard`, `dashboard/listings/[id]/edit`) built on `<Skeleton>` (`src/components/ui/skeleton.tsx`). `<PendingLink>` (`src/components/pending-link.tsx`) is a `next/link` wrapper that portals a fixed top progress bar (`.nav-progress` in `globals.css`, CSS-delayed so fast transitions don't flash) via `useLinkStatus` — used in the header and the back / "view public listing" links. `<ListingCard>` shows a dim+spinner overlay (`CardNavOverlay`, same hook). `ValuationForm`/`PublishListingButton`/`InterestedConfirmForm` gained the existing `<PendingOverlay>`; `ValuationForm` also wraps its post-submit `router.refresh()` in `useTransition` so the overlay stays up through the Market-signal re-render.

## Recommended next step
Share panel + dynamic OG images (WhatsApp share button, QR code on the creator dashboard, per-listing `opengraph-image.tsx`, `sitemap.ts`). Nothing built here yet beyond static OG title/description/cover-image metadata — no share UI, no dynamic image generation. This is the natural next phase: the product's whole distribution model is "share-first" (requirements principle #5 — "every listing must be attractive... when opened from WhatsApp"), and unlike the anti-abuse escalation layer (reCAPTCHA needs a new external credential from the user first), this needs no new credentials and is pure upside. See "Not built yet" below for the other options if priorities have shifted.

## Not built yet (explicitly deferred — see the reuse assessment for what each will fork vs. build new)
- reCAPTCHA v3, suspicion-signal detection, confidence downgrades for suspicious patterns, and an `AbuseSignal`/admin review queue (§9.2–9.3) — reCAPTCHA needs a new external credential (a site+secret key pair scoped to `bid.ihue.in`, unlike everything reused so far) and is explicitly the *escalation* layer on top of the baseline rate limiting that now exists; the other two are genuinely separate, heavier pieces of work.
- A persisted `AggregateSnapshot` (§16) — aggregates are computed live on every page load rather than cached/snapshotted; fine at current volumes, revisit if it becomes a real perf problem.
- Verified-offer mode (the third §7 response tier) and SMS/phone contact — email is the only channel; no SMS provider exists.
- Dynamic OG image generation, full share panel (WhatsApp/QR), `sitemap.ts`.
- Re-opening a closed listing, editing a closure outcome after the fact, a durable/retryable outbox for notifications.
- Listing edit for non-draft listings, handle/slug change redirects, editing `resultVisibility`/`ownerPriceVisibility`/`closureVisibility` after creation.

## Verification convention (same as ihueRating)
`pnpm typecheck && pnpm lint && pnpm test` is necessary but not sufficient — only pure functions are unit-tested (handle validation, the Used Vehicle template validator, YouTube URL normalization). Verify DB-touching flows live: sign in via the mock email provider (any `*.test` address, or `EMAIL_PROVIDER=mock` locally, reveals the OTP on-screen), hit the real API routes, inspect real rows, clean up test data afterward.
